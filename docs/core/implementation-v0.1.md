# 第一轮 Core 实现与验收

依据：[用户架构设计书](architecture-baseline-v0.1.md)。日期：2026-11-19。工作分支：`codex/core-baseline-v01`。

## 本轮交付范围

实现一个可独立运行、可由相同 Command 接口驱动的 Python Core。数据层统一管理卡牌、陆海军、隐藏能力副本和动态得分来源；规则服务不依赖 Node、浏览器或 GUI。新代码不导入旧归档，不复制或运行 Forge / TripleA 源码。

`core/data/architecture_fixture.json` 提供原创机制场景，包含六国席位、11 个虚构地区、测试卡牌、有限预备单位及明确的触发顺序。正式内容包需要独立验收。`evaluation_weights.json` 保存未经强度校准的试验参数。

## 权威状态与执行约束

每个 Token 只保存实例 ID、定义 ID、类型、归属、位置和不可变来源关系，不添加已使用、补给或激活标志。地区和抽象 Zone 共用位置注册表；有序牌区保存实际排列。额外得分令牌可不归属于任何国家，静态地图得分点无需实体化。

公开客户端只收到深度复制后的 Observation 与合法 Command。宿主分配 `controlled_countries`，允许一个客户端管理多个国家；这不是网络身份认证机制。客户端不能提交任意 Operation、直接写入 State 或伪造其他国家选择。Command 还必须匹配当前 `expected_version`，重复、过期和非法指令不改变状态。

每次原子步骤在副本上处理：推进当前帧 → 产生语义结果 → 全量扫描匹配能力 → 验证不变量 → 追加并同步日志 → 发布新状态。日志失败时，不发布该步的棋盘、栈、决策、版本或编号变化。内部能力区迁移不是新的监听事件，避免复位或冷却形成伪触发。

多操作卡牌以逆序存入帧再依次弹出；嵌套能力帧先执行，父帧等待。只允许一个阻塞式 DecisionRequest，未完成选择时 `step()` 不推进。建设、征募、战斗和直接消灭保留不同语义；合法空地战斗即使没有物理变化也成功并产生记录。

潜在受阻止的建设、征募、战斗、消灭先提交 ANNOUNCE 检查点，监听能力完成后才重查合法性并提交原操作。取消关联具体 announcement ID，不提前移动目标单位。卡牌失败后是否停止剩余效果，由该定义的 `failure_policy` 明确指定，合成数据不替正式卡牌作出裁定。

## 能力、费用与重建

- 每个国家有独立的对象池 `OBJECT_POOL`。初始清单登记每张卡、每个能力副本和配套响应的 ID、类型、定义、归属及来源。每个原子步骤和重放步骤都核对清单，规则执行期间只允许位置和区内顺序变化。
- 源卡部署后，其常规能力副本进入 `ABILITY_READY`。一次事件从同一来源的同种可用副本中选一个，支付成功后进入 `RESOLUTION`。无限次对象按 `after: "origin"` 返回原区。一次性对象按 `after: "delete"` 移回对象池。实体卡也可声明这两种去向，原有实体卡继续按卡类进入部署区或弃牌区。
- 限次能力的每个副本在自己结算完成时回池，并通过 `on_settle` 从池里取出一个独立的隐藏响应，放入 `RESPONSE`。符合条件的 `TURN_END` 使该响应进入 `RESOLUTION`，它的效果将先前用过的副本从池移回原区。响应自身最后回池。当前剩余次数等于原区里仍可用的副本数。
- AUTO 与 OPTIONAL 共用相同执行器。可选能力先选择使用/放弃；费用卡逐张选择但不立即消耗，全部重查成功后一次提交支付，防止部分付款或同副本重复付款。持续状态可以修饰能力费用。
- 来源牌离开部署区时，关联的可用副本、正在处理的副本和等待中的响应随之回池，已排队的关联帧失效。
- 不同能力同时触发时按内容声明的优先级结算。同一种响应的多个已部署实例各自排队，所以两次已用次数可以在同一回合末依次归还。
- 连续重建在帧中保存开始时的合格实体 ID 和已处理 ID。每次使用临时副本移除所选原单位、重算建设位置，再一次提交实际移动；等待目标期间不丢失原单位。没有合法目的地时保留原位置。这里采用“临时计算移除 + 原子重建”，没有发布先移除后失败的中间棋盘。

Draw 的全部操作完成后，当前国家提交一次 `TURN_END`。响应区只公开暗置对象数量。命中的响应按定义等待选择或自动执行，支付完成时把实体从 RESPONSE 转入 RESOLUTION。来源对象结算完毕时，`OBJECT_SETTLED` 提交其去向及配置的 `on_settle` 区域转移，并扫描监听该来源完成的新对象。为保持每个 Token 身份唯一，可以将接续对象预置在内容包声明的 SET_ASIDE 区，在上一对象完成后才转入 RESPONSE。

例如，一项每回合可用两次的状态能力在定义中声明 `copies: 2`。两项定义按下表组合。表中的 `CREATE` 表示从对象池取出一个已登记实例，执行器将其作为位置转移写入日志。配置 `same_copy: true` 使两个方向都按来源内对应的副本配对。

| 对象 | 监听事件 | 结算效果 | 结算完成 |
| --- | --- | --- | --- |
| 可用副本 A | 规则指定的使用条件 | 执行本次能力 | A 回池，配对响应 B 从池移入响应区 |
| 隐藏响应 B | 符合归属条件的回合结束 | B 进入结算区，将 A 从池移回可用区 | B 回池 |

卡牌实例由内容包在 `initial_tokens` 中预置。能力的对象池容量从静态副本定义推导，可用 `pool_capacity` 明确指定。效果也可用 `token` 指定精确实例。若指定对象已在场或池中没有匹配对象，执行器记录失败及原因。针对该链条的可执行用例见 [对象生命周期测试](../../core/tests/test_object_lifecycle.py)。

另一组浏览器验收场景演示跨对象选择地区。第一个响应在回合末结算，将另一对象送入 RESPONSE。后者监听前者的完成事件，进入 RESOLUTION，通过 `CHOOSE` 和普通 `TRANSFER` 移动原单位。两种场景都在整个结算栈清空后才推进国家。

## 地图、阶段与计分

MapGraph 加载静态连接并按补给、建设或战斗标签查找可用路径。持续状态可为指定目的增加或移除连接，并可修改补给来源、建设地区及得分。基础供给服务沿定义中的来源与符合条件的单位链求可达集合。盟军单位能否作为中继由内容包配置。

支持设计书确定的六国顺序及 Play → Supply → Victory → Discard → Draw。各阶段通过同一个原子执行器生成补给移除、得分、弃牌选择、补牌及轮末检查。手牌上限、起始抽牌/弃牌、牌库耗尽、局数和胜利门槛均必须显式配置；本轮不猜测真实基础版数值或完整弃牌阶段特殊规则。

同一静态或动态得分来源每次仅汇总一次；动态源的多个副本不会重复计分。TeamScore 为真实整数 VP；未来战略分值仅存在于评价结果中。

## 保存、日志和恢复

持久化记录含游戏/规则身份、序号、轮/回合/父子结算 ID、操作语义、来源目标、变化、结果、前后版本、状态哈希、记录哈希链及状态补丁。重放应用已验证的真实补丁，不重新执行随机选择或扫描监听。

快照含完整牌区顺序、随机状态、栈、已选择/已处理实体、待决选择和记录链头。保存先写临时文件并 fsync，再原子替换；恢复核验格式、规则内容、哈希链、连续序号、前后状态与位置不变量。截断、乱序、重复、遗漏和篡改均拒绝；只有显式指定 `tolerate_truncated_tail=True` 才忽略最后一条未完成行，且不会自动删除现场或在断尾后追加记录。

给 `CommandProcessor.create` 配置 `checkpoint_path` 会写初始快照，并在每个国家回合结束时更新快照；日志由 `OperationLogger(path)` 提供。部署约定为**单一串行写入者**，追加前检查已有链头、游戏/规则身份和文件大小，拒绝混入其他对局或外部写入。原型补丁保存发生变化的完整顶层集合，优先保证正确性；没有声称已通过海量记录性能或数据库多写入者验收。

初始快照保存开局待执行帧。读取日志采用逐行校验。使用 `SaveRepository.resume` 可按验证过的链头继续追加原日志，并在需要时继续未完成的原子结算。测试使用独立进程，在待决选择处强制终止后重新打开同一对局。终局保留胜出操作和卡牌去向，清理所有待执行帧。

对象池快照使用格式 2。读取格式 1 的存档时先验证原哈希链，在下一次写入时按规则清单一次性补齐池和监听实例，并迁移正在冷却的旧副本。旧规则数据中的 `reset_policy` 在载入时展开为结算去向和监听定义。

## AI 边界与评价

真实累计 VP、地图价值、尚未兑现的卡牌潜力和资源修正分项输出，Q(a) 是前后价值差。每个得分点只算一次，已守住地区的单位不会因预备兵力耗尽而丢失驻守价值。来源状态牌与隐藏能力只计一份资源，补给节点移除的边际价值仅用于解释，不再次叠加到总分。

AI 不复制权威 State。模拟器只接受 Observation：所有牌库只保留数量，对手手牌/响应牌用未知占位实体代替，不带真实 RNG、牌序、隐藏副本位置或日志补丁。己方未知抽牌也只产生未知资源，不使用真实顶牌估值。对已公开部署的对手状态牌，按公开定义保守假定其能力可用，不读取其真实隐藏冷却状态。

单次候选模拟只完成当前指令及当前卡牌内部选择，不递归选择下一回合行动。己方选择取较好结果，对已知对手选择取保守结果。节点预算由权重配置给出；超限候选标记 `complete=false, q=null`，不能将部分结算评分冒充完整行动。确定胜负以独立的终局序位优先比较，不会被再大的启发式权重覆盖。待决选择阶段的直接 AI 接口保留确定性合法选项回退，不宣称具有成熟策略。

## 运行

```powershell
npm run core:setup
npm run core:test
npm run core:demo
npm run core:play
npm run check
```

Python 3.11+，Core 运行本身仅使用标准库。测试依赖锁定在 `core/requirements-dev.txt`，本机隔离于 `core/.venv/`。本机 Python 基础运行时从冻结旧环境**复制**到新 `.runtime/python/` 后运行，未执行或修改归档中的解释器。新克隆使用自行安装的 Python，可通过 `QMG_PYTHON` 指定。

演示实际执行一次多步骤卡：获得 1 VP → 阻塞选择建设地区 → 完成建设 → 再获 2 VP；然后核对快照/日志重放，并输出单步 AI 候选及分项评分。演示使用临时目录，结束后不保留游戏资料。

## 仍待确认的正式规则与下一步

正式第二版卡牌清单、文本/版本、铁路运输的真实卡文、能力复位/同时触发优先权、动态地图/得分牌清单，以及正式初始化/弃牌阶段细则均未由本轮合成数据决定。下一轮应先完成规则内容包及逐机制官方案例，再接可玩 GUI；不能用此 Core 机制验收声称整款游戏、全部真实卡牌或高强度 AI 已完成。

本轮工程选择包括白名单 JSON 指令、JSONL 日志和可调的 128 节点模拟预算。验收台使用 Python 标准库 HTTP 和浏览器表单作为接入样例，完整客户端技术栈可独立确定。改变工程选择时需要保留失败样例及重放兼容约定。
