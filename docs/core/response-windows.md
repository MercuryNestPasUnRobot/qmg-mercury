# Core 响应时机验收

Core 将每个规则检查点生成的响应窗口放入现有结算栈。窗口登记当时命中的实体 ID，候选仍留在手牌、状态、响应或可用区。轮到候选时重新检查来源位置、有效的宣告、触发条件、代价和起始效果，选中后才将对应对象转入待结算区。刚获得的卡只能参加之后的新时机。

数字较小的优先级先处理。同一级跨席位从回合玩家开始按固定回合顺序处理。同一席位的同级可选响应由该席位选择先发动哪一个。放弃会跳过该席位的这个优先级，下一优先级仍可选择。自动监听在同一席位同一级的可选响应前执行，同级自动监听按实体 ID 稳定排序。

回合玩家在一个窗口内只能发动一个可选响应，此限制跨越该窗口内的全部优先级。嵌套操作产生的新事件有自己的响应窗口。其他玩家可以在同一窗口依次发动多个响应，每个都按结算到它时的状态复核。自动监听仍按规则执行，包括回合末归还多个副本。

## 结算实例

| 场景 | 验收结果 |
| --- | --- |
| 主卡先打一再建一，首战触发手牌增援额外建一 | 原卡打一 → 增援建一 → 原卡建一 |
| 打一同时可以额外打一或额外建一，回合玩家选择额外打一 | 原卡打一 → 响应额外打一 → 新战斗开新时机 → 原先待选的建一响应可在新时机发动 |
| 同一场景选择额外建一 | 原卡打一 → 响应额外建一 → 首战窗口结束 |
| 非回合玩家有两个同级响应 | 该玩家选择先后，两次均可结算，之后恢复原操作 |
| 响应中触发新监听 | 新窗口及其子效果先完成，再返回原窗口或原卡。剩余响应按当前局面复核 |
| 先处理的响应占据后续响应的目标，或取消原宣告 | 后续响应复核失败，同一窗口继续处理尚能成立的响应，原卡按其失败策略继续或结束 |

## 不变量与验证

手牌增援在发牌、抽牌或回手后即可监听。选择前只向对应席位提供响应对象和选项，手牌和盖放牌的身份在揭示前保持隐藏。人工和 AI 提交相同的版本化 CoreAPI 指令，无法直接移动实体。

验收核对了对象 ID、定义、所属方和来源的不变性，每个对象始终只占一个合法位置。待决时保存和恢复仍得到同一响应选择，过期指令会被拒绝。已完成的卡与响应清空结算栈及待处理区，限次副本继续由独立回合末监听恢复。规则包、对局快照与操作流水各自保存。

`npm run core:test -- tests/test_response_windows.py` 可运行本页示例。整体检查用 `npm run check`。重新迁移的本地卡库为新版固定数据指纹，已有对局仍使用其存档记录的原指纹目录。
